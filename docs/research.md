# 领域调研与设计取舍

> 目的：说明“为什么自研、为什么不直接引现成库”，以及各设计点的取舍依据。

## 1. 主流方案盘点

| 方案 | 定位 | 依赖 | 与底座契合度 |
| --- | --- | --- | --- |
| robfig/cron | 定时调度（cron 表达式） | 0 | 只解决调度，不解决执行池/重试/关闭 |
| go-co-op/gocron | 调度 + 简单任务 | 0 | 功能重合度高，但风格与 errx/logx 不一致 |
| asynq | Redis 分布式异步队列 | go-redis | 分布式能力过剩，自用单机场景引入 Redis 依赖 |
| river | PostgreSQL 持久化任务 | pgx | 需要数据库，违背“轻”的路线 |
| machinery / gocraft/work | 分布式任务队列 | 重 | 明显过度 |

## 2. 自研结论

自用项目需求是**单进程内的执行与调度基础设施**，现成库要么功能过剩
（asynq/river），要么只覆盖一半（robfig/cron 只做调度）。
自研成本可控，且可以做到：

- 与 errx / logx 生态原生打通（错误码、结构化日志、错误链）；
- 统一质量门禁（100% 覆盖、race、fuzz、三平台 CI）；
- 只实现需要的语义：异步、延迟、定时、超时、重试、防重入、优雅关闭；
- 0 第三方依赖，后续按需加适配器（Redis 队列、PostgreSQL 持久化）。

## 3. 关键取舍

### 3.1 队列实现：channel vs 自研队列

选 channel：

- 原生并发安全、阻塞/非阻塞语义清晰；
- 与 worker 池天然配合，无锁热路径；
- 代价：不支持按优先级消费——jobx 不需要优先级（延迟任务由延迟堆解决）。

### 3.2 延迟任务：时间轮 vs 最小堆

选最小堆 + 单 timer：

- 时间轮适合海量同周期定时器（如网络框架），自用任务量级
  （数百-数千）下最小堆 O(log n) 足够；
- 单 timer 避免每条目一个 goroutine/timer 的资源浪费；
- 关闭时堆可整体遍历丢弃，语义清晰。

### 3.3 cron 解析：自研 vs robfig/cron 依赖

自研：

- 只需 5/6 字段常用语法（`*`、`*/n`、`a-b`、`a,b,c`、`?`）；
- 可以精确控制错误语义（errx 错误码、字段定位）；
- 不引入第三方依赖；未来需要 `L/W/#` 时再扩展。

### 3.4 同名冲突：默认跳过

自用业务常见重复提交（Webhook 重放、定时器漂移、同一订单的
重复超时检查），同名任务并发执行往往产生重复副作用。但“如何处理
冲突”没有唯一答案，因此做成可配置策略：

- `ConflictSkip`（默认）：静默跳过新提交。对调用方零打扰
  （返回 `ErrSkipped` 可感知但业务可忽略），日志与 Metrics
  记录被跳过次数；适合“兜底任务重复触发无害”的场景；
- `ConflictReplace`：取消旧任务并执行新任务。适合“旧数据已过期、
  必须以最新状态执行”的场景（如缓存刷新、订单状态重算）；
- `ConflictAllow`：允许并发。适合天然可并行的任务（幂等写入、
  无共享状态的聚合）。

默认 Skip 的依据：安全（不破坏旧任务）、可感知（非静默吞错）、
代价最小。Replace 的取消是“尽力”语义：排队/延迟可精确移除，
执行中依赖 Handler 协作 `ctx.Done()`，文档明确不保证严格串行。

### 3.8 简易调度包装

`EveryMinuteAt` / `EveryHourAt` / `DailyAt` / `WeeklyAt` 是 cron
表达式的**受约束包装**，而非独立调度引擎：

- 高频场景（每小时某分、每天定点）手写 cron 易错（字段顺序、
  范围、6 字段与 5 字段混淆）；
- 包装方法以具名参数 + 越界校验消除该类错误，内部等价构造
  cron 表达式，触发语义（时区、下次计算）与 `Cron` 完全一致，
  不引入第二套调度逻辑；
- 完整能力仍由 `Cron` 提供，包装不限制扩展。

### 3.5 重试退避：确定性指数

不引入随机抖动：

- 自用场景无“惊群”压力（不像分布式定时器集群）；
- 确定性便于测试与日志排查；
- 若未来需要抖动，作为选项扩展（接口预留 `RetryDelayFunc`）。

### 3.6 关闭语义：先排空、再等待、超时强杀

与 webx 优雅关闭一致：

- 拒绝新任务，避免“关一半进来一半”；
- 排空延迟堆（丢弃），消费完就绪队列；
- ctx 超时后取消执行中任务 context，避免进程退不出。

### 3.7 Metrics：回调注入 vs Prometheus 直连

回调注入：

- 保持 0 依赖；
- 业务/未来 metricsx 决定接到 Prometheus 还是自研指标端点；
- 与 cachex 的 Metrics 注入模式一致（底座风格统一）。

## 4. 与既有底座的分工

| 底座 | 分工 |
| --- | --- |
| errx | jobx 全部错误语义与错误码 |
| logx | 结构化日志（`jobx_` 前缀字段） |
| cachex | 业务可在 Handler 内使用；未来“去重/防击穿”与 jobx 防重入互补 |
| confx | 业务用 confx 加载 worker/队列等配置后传入 jobx |
| webx | 业务在 webx 启动流程中拉起 jobx（生命周期组合，不耦合） |
| dbx | 持久化 Store 适配器（v0.5+）可基于 dbx 实现 |
| authx | 无关（任务鉴权由业务处理） |
